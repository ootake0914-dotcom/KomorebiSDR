# 特定局の音揺れ診断手順書

「特定の局だけ音がデカくなったり小さくなったりする」場合の切り分け手順。
推測で弄らず、受信健康ログを取って犯人を特定する。

## 1. 前提

- `main.py` を `RTLSDR` フォルダから `python main.py` で起動していること
  （配布exeや別フォルダのコピーでは記録されない）
- `signal_logger.py` のコードが入った後に `main.py` を**再起動**していること
  （起動しっぱなしの古いプロセスには記録機能がない）

## 2. 記録の確認

受信開始から10秒後に PowerShell で確認する。

```powershell
dir "$env:APPDATA\KomorebiSDR"
```

`signal_log.csv` があり、更新時刻が現在なら記録中である。
注意: `%APPDATA%` ではなく `$env:APPDATA` と書く（PowerShell では `% %` は展開されない）。

## 3. 測定

1. 問題の局に選局する（例：東京FM 80.0MHz）
2. **選局・モード・音量を触らずに** 3〜5分聴く
3. 要約コマンドを実行する（第2引数は周波数Hz。±50kHzで切り出す）

```powershell
python signal_logger.py "$env:APPDATA\KomorebiSDR\signal_log.csv" 80000000
```

### 自動ブランキングについて

起動後15秒と、各選局から8秒はAFC・PLL等の過渡が載るため自動で記録しない。
そのため「開いてすぐの1回目の選局」はログに混入しない。測定中の選局操作も
同様に前後8秒が除外されるが、確実のため測定中は触らないこと。

## 4. 結果の読み方

出力は `stats`（指標ごとの平均/標準偏差/最小/最大）と `hints`（犯人候補）からなる。

| ヒント | 意味 | 対応 |
|---|---|---|
| パイロット不安定 | ステレオ⇔モノラル往復（`blend`/`pilot_lock` のstdが大） | 1.4秒以内の瞬断はフライホイールで自動保持（`_pilot_hold_max`）。持続する場合はマルチパス/弱電界対策へ |
| 反射波検出中 | `multipath_gain` 平均が0.9未満。都市部反射が常駐 | マルチパス抑圧の効かせ方・時定数を調整 |
| ヒス推定が変動 | `nr_gain` のstdが大。NRが番組連動 | NR推定の平滑化（実施済み: `_update_stereo_nr` の分母τ2.5秒） |
| AFC大変動 | `afc_hz` の最大−最小が500Hz超 | 選局過渡は自動除外済みのため、残れば送信/ドングルドリフト |
| 電界変動大 | `s_units` のstdが大 | 遠距離フェージング。アンテナ・設置の検討 |
| ゲイン探索中 | `gain_db` のstdが大 | 自動ゲイン未収束。強入力・混変調の疑い |
| 電波側は安定 | 上記なし | 番組・音声処理側（AGC/EQ等）を疑う |

### 参考値（東京FM 80MHz・約6分の実測例）

- `blend`: std 0.0（固定）→ ステレオ中核は無罪
- `nr_gain`: std 0.31、`cut_hz`: std 3256 → NRポンピング有罪（修正前）
- `multipath_gain`: 平均 0.67 → 反射波が常駐
- `s_units`: std 0.03 → 電界は安定、搬送波フェージングではない

## 5. よくある躓き

| 症状 | 原因 |
|---|---|
| `ログがありません` | 受信が始まっていない／別フォルダのプロセスが動いている |
| `データ不足` | 10行未満。1分以上待って再実行 |
| 一瞬で窓が閉じる | `.py` をダブルクリックしている。PowerShellから実行する |
| AFCだけが異常 | 測定中に選局・シークした。触らずに取り直す |
